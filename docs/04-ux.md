# 4. User Experience & Interaction

## 4.1 Product principles

1. **The plan is a proposal, never a fait accompli.** No AI output mutates the athlete's
   calendar without an explicit accept. Trust is the product.
2. **Every number is explainable.** Tapping any load opens "where this came from": basis,
   percentage, measurement date, any clamp applied.
3. **Logging must be thumb-speed.** The session player is used mid-set, one-handed, sweaty,
   sometimes offline. Two taps to log a set; RPE is the only mandatory field.
4. **Absence is data.** A skipped session is a first-class logged event with a reason, not a
   gap. It is the highest-signal input the adjustment engine gets.

## 4.2 Screen map

```
Onboarding (6 steps) ──▶ Generating… ──▶ ┌── Today ──── Session Player ── Session Debrief
                                          ├── Calendar (week / month)
                                          ├── Progress
                                          └── Coach (adjustments + Q&A)
```

### A. Onboarding — 6 steps, ~3 minutes

| Step | Asks | Writes | Design note |
|---|---|---|---|
| 1 Goal | "What are you training for?" + optional event date | `goal_statement`, `goal_event_date` | Free text + 4 preset chips. The event date silently arms the taper rule. |
| 2 Background | years climbing, years structured training, discipline, grades (limit / flash / onsight / redpoint) | `athlete_profiles`, `grade_records` | Grade picker in the athlete's own system, V-scale ⇄ Font toggle. Never make them convert. |
| 3 Schedule | day-by-day availability + minutes per day | `availability` | A 7-chip row with a duration stepper. This is a *budget*, and the AI must respect it. |
| 4 Equipment | multi-select cards; hangboard expands to edge sizes + plate increment | `athlete_equipment` | Drives which protocols are even reachable. "No hangboard" is a supported answer, not a dead end. |
| 5 Health | current pain?, past injuries (structure + when) | `injuries` | Two-question pattern: pain (stop condition) is asked separately from soreness. Plain-language structures with a hand diagram, not medical vocabulary. |
| 6 Baseline | "Do you know your max hang?" → enter, or **Test later** | `assessments`, `derived_metrics` | **Never block on this.** "Test later" → estimated baselines, `is_estimated = true`, week 1 becomes an assessment week, all intensities clamped to ≤ 0.85. |

Then: a generation screen that shows real progress over SSE ("Assessing your baselines →
Shaping week 1 → Placing recovery"), 20–60 s, with the block summary revealed as a card.
If generation fails, the fallback template block is shown, labelled as such.

### B. Today

The default landing screen. One hero card:

- Session title, primary-stimulus colour, duration, **why today** (one line from `coaching_note`)
- Pre-session readiness strip — sleep / soreness / stress, three taps, optional
- Primary CTA **Start**; secondary **Move** / **Swap** / **Can't train today**
- On a rest day the hero card says so, with equal visual weight. Rest is prescribed, not absent.

### C. Calendar

- **Week strip** (default) — 7 columns, each session a chip coloured by stimulus; a legend maps
  colour → stimulus so the athlete learns the clustering model just by looking at their week.
- **Month view** — density view, deload week visually distinct, taper window shaded.
- **Drag to move** → immediate client-side re-check against recovery gaps and availability.
  Illegal drops are refused *in the gesture*, with the reason ("needs 48 h after Tuesday's
  max hangs"), not after a round trip. This is where users learn the science.
- Long-press a session → Swap (same-stimulus alternatives from `substitution_hint`),
  Move, Skip (with reason), View details.

### D. Session player

The one screen that must be perfect.

- Vertical list of items in mandatory order; current item expanded, rest collapsed.
- **Protocol-aware timers**: `lattice_repeaters_7_3` renders a 7 s/3 s × 6 clock with haptics
  on every transition; `eva_lopez_maxhang_maw` renders a 10 s countdown then a 3:00 rest timer
  with a "next set" prompt; `four_by_four` renders a set counter and inter-set rest.
  Timers run on the UI thread (Reanimated) so they don't drift when JS is busy.
- Per set: prescribed load pre-filled, tap to edit actual, RPE dial (1–10), **✓ Done**.
- **Tier-0 autoregulation happens here, offline, no LLM**: if RPE ≥ 9 lands before the final
  set, the remaining sets' loads drop 5–10 % immediately with an inline note ("dropping to
  26 kg — protect the quality of the last two sets"). Instant, deterministic, reversible.
- Pain button, always visible: ends the session, sets `pain_flag`, opens the safe-mode flow.
- Everything writes to the local SQLite queue first and syncs when there's signal.

### E. Session debrief (≤ 15 s)

Session RPE dial · soreness · one optional free-text note · "How did it feel?" chips
(*crushed it / on target / heavy / something hurt*). This screen is the trigger point for
Tier-1/2 adjustments.

### F. Progress analytics

Four sections, in decreasing frequency of use:

1. **Strength** — `finger_load_index` over time (the headline metric: total load ÷ bodyweight
   on 20 mm), `pullup_strength_ratio`, min edge depth. Assessment points as markers, plan
   periods as background bands so improvement is attributable to a block.
2. **Load** — weekly volume stacked by stimulus colour (teaches clustering at a glance) +
   the acute:chronic ratio with the 0.8–1.3 band shaded. Outside the band, an explainer.
3. **Execution** — prescribed vs. actual load scatter, and RPE distribution against the 7–8
   target zone. An athlete consistently at RPE 6 is under-loaded; the chart says so plainly.
4. **Performance** — grade progression by discipline, sends logged, adherence %.

Rule: every chart answers one question, stated as its title ("Is my finger strength
improving?"), not a metric name.

### G. Coach

Adjustment cards (below) plus bounded Q&A — "why am I doing repeaters?", "what is a
half-crimp?" — routed to a cheaper model with the same doctrine prompt, **read-only**: the
chat surface can explain the plan but can never mutate it. Plan changes only ever happen
through the reviewed adjustment path.

## 4.3 Accessibility & craft notes

- Stimulus colour is always paired with a label or icon — never colour alone.
- Timer states announced via `AccessibilityInfo` for screen readers; haptics carry transitions
  for anyone who can't watch the screen mid-hang.
- Type scale ≥ 17 pt for anything read at arm's length on a wall.
- Dark theme is the default: gyms are dark, phones are on the floor.

## 4.4 AI adjustments — the tiered response model

The central interaction. Not every deviation deserves an LLM call; most deserve none.

| Tier | Trigger | Who decides | Latency | Athlete sees |
|---|---|---|---|---|
| **0 — in-session** | RPE ≥ 9 before the last set; failed rep | Client, offline | instant | Remaining sets auto-adjust, inline note |
| **1 — deterministic** | One session outside the RPE target zone | Engine rule table | < 1 s | "Next hang session adjusted to 90 %" toast |
| **2 — AI revision** | Pattern: RPE ≥ 9 twice · ≥ 2 sessions missed · ACWR > 1.3 · equipment/schedule change | LLM patch, validated | 5–20 s, async | Adjustment card with diff, accept / decline |
| **3 — safety** | Pain flag, or a new injury record | Hard-coded rules only | instant | Protocol suspended, substitution offered, referral prompt |

Tier 3 is never delegated to the model. Ever.

### Worked example: "Too hard — RPE 9/10"

**1. Capture.** The debrief writes `session_rpe = 9` plus per-set rows to `session_logs` /
`set_logs`. Offline-safe.

**2. Deterministic evaluation first.** The engine consults the autoregulation table
(§2.4). One RPE-9 exposure → *hold intensity on the next same-stimulus session*. That is a
**Tier 1** change: one field, no model call, no confirmation dialogue, a toast. Most RPE-9
reports end here — and that is the point. A system that convenes the AI over every hard
session is slow, expensive, and feels twitchy.

**3. Escalation.** It becomes **Tier 2** only if the signal is a pattern: a second
consecutive RPE ≥ 9 on that stimulus, or combined with missed sessions, or ACWR > 1.3.
A revision job is enqueued.

**4. The revision call.** Cached doctrine prompt + `system-revise.md`, with a payload of
`remaining_sessions` (future only), the `deviation_report`, and the athlete's note. The model
returns a **patch**, not a plan:

```jsonc
{
  "schema_version": "1.0.0",
  "severity": "moderate",
  "acknowledgement": "Two hang sessions at RPE 9 in a row means we're ahead of what you're recovering from. I'm holding your hang intensity where it is, pulling one 4×4 set out of next week, and bringing your deload forward by a week. Your hangs should feel hard on the last two sets — not like a fight from set one.",
  "operations": [
    { "op": "adjust_intensity", "item_id": "w3_maxhang", "from_pct": 0.95, "to_pct": 0.90,
      "reason": "Holding load — you hit RPE 9 on both hang sessions this week." },
    { "op": "adjust_volume", "session_id": "w3_thu", "item_id": "w3_4x4", "sets": 3,
      "reason": "One less 4×4 set so Thursday doesn't eat into Saturday." },
    { "op": "convert_to_deload", "week": 4,
      "reason": "Bringing your recovery week forward — you've earned it early." }
  ],
  "requires_confirmation": true
}
```

**5. Validate before display.** The patch is applied to a working copy and re-run through the
full validator (clustering, recovery gaps, weekly caps, availability, taper). A patch that
breaks a constraint is bounced back to the model with the violation list, twice, then dropped
in favour of the deterministic Tier-1 action. **The athlete never sees an invalid proposal.**

**6. Present as a reviewable diff.**

```
┌────────────────────────────────────────────┐
│  Coach suggests 3 changes      [ Why? ▾ ]  │
├────────────────────────────────────────────┤
│  "Two hang sessions at RPE 9 in a row      │
│   means we're ahead of what you're         │
│   recovering from…"                        │
│                                            │
│  Wed 12  Max Hangs      32kg → 30kg        │
│  Thu 13  4×4s           4 sets → 3 sets    │
│  Week 4  Build week     → Deload week      │
│                                            │
│  [ Accept changes ]      [ Keep my plan ]  │
└────────────────────────────────────────────┘
```

`minor` → inline card on Today. `structural` → full-screen before/after diff.
**Declining is a first-class outcome**: recorded in `plan_adjustments.athlete_response`, and
the decline itself becomes context for the next block ("this athlete prefers to push through
— program slightly conservative and let them add").

**7. Commit atomically.** On accept: write a new `plan_versions` row (`supersedes_id` → current),
re-project `plan_sessions` / `plan_items` with freshly resolved loads, flip the block's active
version, and complete the `plan_adjustments` audit row — all in one transaction. Past sessions
are untouched; only future ones move. Undo is trivial because the old version still exists.

### Anti-patterns to design out

- **Silent rewrites.** The calendar changing overnight with no explanation destroys trust faster
  than any bad prescription.
- **Adjustment spam.** Rate-limit Tier 2 to at most one proposal per 48 h; batch signals.
- **Over-correction.** A single hard session is not a trend. The tier table exists precisely to
  stop the model relitigating the block every time someone sleeps badly.
- **Hiding the reasoning.** Every adjustment card carries a "Why?" affordance that shows the
  observation → rule → change chain. Users who understand *why* adhere; users who don't, churn.
